# 无 root 版真机验证清单

本项目的起点是**验证优先的原型**。目标只有一个：用最小的代价回答「无 root 条件下，能不能把 ColorOS 自由窗唤起来」。其余能力（扇形菜单、角落手势）都已实现，但它们不是风险点。

## 前置条件

- Android 15（API 35）及以上的 ColorOS 设备。
- 构建：用 Android Studio 打开工程选 `app` 运行配置；或命令行 `./gradlew :app:assembleDebug`。
- 产物路径：`app/build/outputs/apk/debug/FlymeFreeform-<版本>-Debug.apk`。

### 命令行构建环境（本机已验证通过）

| 组件 | 版本 | 位置 |
| --- | --- | --- |
| JDK | Temurin 17.0.20.1 | `~/Library/Java/JavaVirtualMachines/temurin-17.jdk` |
| Android SDK | platform `android-37.0`、`android-36`；`build-tools;36.0.0`（AGP 9 默认）与 `37.0.0`；`platform-tools` | `~/Library/Android/sdk` |

SDK 位置写在根目录 `local.properties` 的 `sdk.dir`（该文件已被 `.gitignore` 忽略）。
若换机器构建失败，先确认上述 SDK 组件齐全，再看 `gradle/libs.versions.toml` 里 `shizuku = "13.1.5"` 能否解析。

> 注意：本模块**不要**显式声明 `org.jetbrains.kotlin.android` 插件——AGP 9 自带 Kotlin 支持，
> 额外声明会让 Gradle 报 “plugin is already on the classpath with an unknown version”。

## 第 1 步：确认「以小窗启动」是否可行（**这一步决定全案成立与否**）

1. 打开 App，授予「显示在其他应用上层」。
2. 等应用列表加载完成，任选一个应用点「加入扇形」。
3. 点「用第一个扇形应用测试启动」。
4. 看「启动验证」区域与「运行日志」。

判读：

| 现象                                                 | 含义                                     | 下一步                                                                    |
| -------------------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------- |
| `[direct.startActivity] 成功`，且**确实进入了小窗**（不是全屏）     | 最理想：零特权就能用，Shizuku 都不需要                | 直接进入第 2 步                                                              |
| `[direct.startActivity] 成功`，但**是全屏**               | ColorOS 忽略了 `windowingMode=100`，参数没被接受 | 试 `[shizuku.am]`；仍不行则查厂商是否要求特定调用方                                      |
| `[direct.startActivity] 失败 被拒绝（SecurityException）` | 系统校验了调用方身份                             | 授权 Shizuku 后重试，看 shell 身份是否被接受                                         |
| `[shizuku.am] 失败 ... unknown option ...`           | 该 ROM 的 `am` 不支持 `--windowingMode`     | 点「复制 am 命令」，粘到自己的 adb/Shizuku 终端里逐个试 `am help`、`am start --help`，找等价参数 |
| 两个策略都失败                                            | 无 root 路线的核心假设不成立                      | 停止投入，保留现有 Xposed 版本                                                    |

**判定标准：屏幕上出现的是自由窗/小窗形态，而不是全屏。**「命令返回成功」不等于「进了小窗」，一定要看画面。

## 第 2 步：确认角落悬浮窗能不能拿到触摸

1. 打开「总开关」，确认服务变为「运行中」，状态栏出现常驻通知。
2. 从屏幕左下角**斜向内上滑**，观察是否展开扇形菜单并跟随手指选中。

若唤不出：

- 先看日志里有没有 `GESTURE_ACTIVATED`。
  - **没有**：触摸根本没到悬浮窗，或手势判定没通过。触摸区现在**始终从屏幕边缘起算**（见下面「向内延伸」的说明），所以起手位置不用迁就任何值；优先把「触发范围」调大。
  - **有但菜单不出现**：看是否出现 `MENU_EMPTY`（没固定应用）或 `MENU_ADD_FAILED`。
- 「触发范围」默认 96dp。触摸区是**紧贴屏幕角落的一个方块，边长就是这个值**（宽和高相同）。如果手指需要滑很远才激活，这个值偏小；如果误触频繁、或角落内容被挡得多，调小。
- 「边缘让位」默认 12dp，是屏幕左右边缘**让给系统**的宽度。

  > 这个参数改过两次语义，值得记清楚现在的定义：
  >
  > 1. 最早它是「把整块触摸区向内平移」——用户调大后手指仍从最角落起手，却落在触摸区之外，表现为「一改边缘让位就再也唤不出菜单」。已废弃。
  > 2. 然后它变成「触摸区在触发范围之外再向内多覆盖多少」，**直接加进触摸区宽度**。这个更糟：用户调到 80dp 时，角落方块被撑成 **157dp 宽的一条横带**，屏幕底部一大片全被独占窗口吃掉——就是「屏幕下面点不动」。
  > 3. 现在它**只决定靠外那一条边不申请手势排除**，完全不影响触摸区大小。上限也从 80dp 收到 24dp，足够覆盖 ColorOS 的侧滑返回触发带。

- **触摸条底边至少让开屏幕底部 20dp**（代码里是 `CornerGeometry.MIN_BOTTOM_INSET_DP`）。这一条比导航条高度本身更关键：部分 ROM 在手势导航模式下把 `navigation_bar_height` 报成 0，触摸条会贴死最底边，把「上滑回桌面 / 上滑进多任务」的感应区盖住。那**是手势不是点击，透传救不了**，整个底部导航就废了。
- 三键导航下不生效（日志会标出手势导航为「否」）。这是设计如此，不是缺陷。

手势激活后，角落触摸条会被**临时扩展成全屏**。这是必须的：原来它只有角落一小块，手指一旦滑出这块矩形，系统会重新做命中测试、把后续事件转给下层窗口，本进程随即收到 CANCEL——表现就是「呼出后不能悬停、一移开就消失」。扩展后整条指针流都留在本窗口内，手指可以停在任意位置，抬手才提交。

若日志出现 `TRIGGER_RESIZE_FAILED`，说明窗口尺寸调整被拒绝，悬停问题会复现，需要单独排查。

## 第 3 步：确认整体链路

左下角斜上滑 → 扇形展开 → 滑到某个应用 → 松手 → 该应用以小窗打开。日志会打印  
`GESTURE_COMMIT` 与 `LAUNCH_ATTEMPT`，可以据此定位是手势问题还是启动问题。

## 第 4 步：验证「窗外点击关闭」（无障碍近似方案）

这一块**不是原版行为的等价替换**，是近似实现。验证重点有两个：「能不能用」，以及「副作用能不能忍」。

1. 在设置页「窗外点击关闭」区块，先打开「调试描边」。
2. 点「打开无障碍设置」，在系统设置里找到「Flyme 小窗 · 窗外点击关闭」并开启。
3. 回到 App，打开「启用窗外点击关闭」。
4. 用第 1 步的方式开一个小窗，观察屏幕上是否出现**半透明红色遮罩**（只有开了调试描边才显示）。

判读：

| 现象                   | 含义                | 下一步                            |
| -------------------- | ----------------- | ------------------------------ |
| 小窗四周出现红色遮罩，中间小窗区域是空的 | 小窗识别正确            | 关掉调试描边，点窗外试关闭                  |
| 完全没有红色遮罩             | 没识别到小窗            | 看日志有没有 `OUTSIDE_TAP_NO_WINDOW` |
| 遮罩盖住了小窗本体或标题栏        | 边界推断偏大            | 调大「遮罩外扩」，把标题栏让出去               |
| 遮罩盖住整个屏幕（含小窗）        | 小窗窗口的 bounds 就是全屏 | 该 ROM 上这套识别方式不成立，只能放弃          |

### 关闭动作：点小窗**底部的小横条**

**关键区分**：「关闭小窗」和「返回」不是一回事。返回键投给焦点窗口，应用里有回退栈（WebView、二级页）时会先被吃掉，表现就是「点一次不关、要两次」；在深层页面里则是「一直往上一层退」——那根本不是关闭小窗。

**所以这个功能不再用返回键兜底。** 目前 ColorOS 上与 `exitFlexibleTask` 语义等价、且**一次就能关掉**的做法是点小窗**底部那条小横条**。注意不是右上角那个按钮——点它会先弹出二级菜单，还得再选一次。小横条属于 system_server 进程里的 `FlexibleCaptionView`，**不在无障碍节点树里**，只能按坐标点，因此落点必须校准。

设置页「关闭方式」按钮循环切换：

| 策略 | 做法 | 日志 |
| --- | --- | --- |
| **点小窗底部小横条**（默认） | 无障碍手势点「横向 X% 窗宽 / 距底边 Y dp」那个点 | `CLOSE_ANCHOR_TAP` |
| Shizuku 返回键 | `input keyevent KEYCODE_BACK` | `OUTSIDE_TAP_SHIZUKU` |
| 无障碍返回键 | `performGlobalAction(BACK)` | `OUTSIDE_TAP_BACK` |
| 点系统关闭入口 | 在无障碍节点树里找关闭节点 | `CLOSE_ENTRY_SCAN` |

> 最后那一项是**已确认无效**的历史策略，保留只为兼容旧配置：标题栏属于 system_server，不会向无障碍暴露节点树，扫描必然落空。

**落点为什么按「底边 + 百分比宽度」量**：小横条在小窗**底部**，基准取底边——用顶边当基准的话，小窗一被拉高，落点就会停在半空。横向用**占窗宽的百分比**而不是 dp，是因为小窗可以拉伸，写成固定 dp 会越拉越偏；`50` 就是水平中点。

### 校准落点（默认策略没关掉时先做这个）

1. 先开一个小窗（可以就让它悬浮在设置页上方）。
2. 设置页打开**「显示关闭落点准星」**。
3. 小窗底部会出现一个**红色准星**，那就是每次点击的落点。
4. 调「落点横向位置（占小窗宽度 %）」与「落点距小窗底边（dp）」两个滑块，让准星正好压在小横条上。
5. 对准后关掉准星。

默认是「横向 50% / 距底边 8dp」。若准星落在小窗**下沿之外**，把「距小窗底边」调成**负值**。

复检（320 ms）：关掉了 → `OUTSIDE_TAP_CLOSED`；还在 → 按**同一策略**重试一次（落点向上抬 6dp）→ `OUTSIDE_TAP_RETRY`；仍不行 → `OUTSIDE_TAP_STILL_OPEN`。

**任何情况下都不会再自动发返回键**——那正是「点一次退一层」的来源。

`OUTSIDE_TAP_STILL_OPEN` 反复出现时：先做上面的校准；仍不行说明该 ROM 的小横条位置特殊，可改用「Shizuku 返回键」，或打开**「强力关闭」**用 Shizuku 执行 `am force-stop <包名>` 兜底（日志 `OUTSIDE_TAP_FORCE`，代价是应用被整体杀掉，默认关闭）。

> **0.1.6 修了一个「落点算错」的真 bug**：`close_anchor_y_dp` 这个 key 和旧版「距顶边」用的是同一个字符串，历史脏值会直接算出一个落到小窗**外**的坐标（0.1.5 日志里 `CLOSE_ANCHOR_TAP (636,2090)` 的 x 比小窗左边缘 642 还靠左）。现在落点换成了新 key `close_bar_x_percent` / `close_bar_y_dp`，并在首次启动时**无条件删旧值、写入默认 50% / 8dp**，装上就是干净的。
>
> **0.1.7 又修了两个「点两次才关」的根因**：
>
> 1. **窗口识别挑错对象**。`observeLayout` 早先挑「面积最小」的次全屏窗口，本意是避开前台全屏应用，但小窗一失焦 ColorOS 会把它轻微缩小，同时冒出来的小浮层（气泡、把手条）会在「最小竞赛」里胜出——落点算到完全不相干的矩形上。现在改挑 band 内**面积最大**的窗口（小窗本体永远是最大的那个）。
> 2. **复检太快，把「正在退出」误判成「没关掉」**。点窗外那一刻小窗失焦、会先缩小再收起，这段退场动画约两三百毫秒。早先 320ms 就复检，正好撞在动画中途，于是往一个正在变形的窗口上又补一刀——补的那刀落点自然偏。现在复检延迟提到 450ms。
>
> 另外 `am force-stop` 对正在显示自由窗的前台进程会返回 `process hasn't exited`——那是进程已在退出流程中的正常现象，不是失败。0.1.6 起把它当成功处理，不再反复折腾，避免把应用搞到短暂卡死。
>
> **新的 `OUTSIDE_TAP_TRIGGERED` 日志会带上 `窗口=[l,t,r,b]`**，若还关不掉，把这一行发我——能直接看出识别到的小窗矩形到底对不对，不用再猜。

**这几项必须看画面，不能只看日志**——日志显示点击已提交，不代表小窗真的关了。

### 已知副作用（先知道再决定要不要开）

1. **窗外触摸全部被吃掉**——这正是功能本身，但也意味着开着小窗时点不到它后面的应用。
2. **有三处永远不生效**：状态栏区域、底部手势带、以及**软键盘弹出的区域**。前两处主动让开，避免吃掉下拉状态栏和上滑回桌面；键盘那处主动让开，避免在小窗里打字时点一下字母就把小窗关掉。
3. **拖动/缩放小窗时会短暂错位**——遮罩重排依赖无障碍的窗口变化事件，有几十毫秒延迟。觉得碍事就打开「只遮左右两块」。
4. **小窗标题栏可能被盖住**——正是「遮罩外扩」要解决的问题，默认外扩 12dp。

### 键盘避让

在小窗里点输入框唤起软键盘后，**底部遮罩会收缩到键盘上沿**，键盘本身不再被遮罩覆盖，所以点字母、点候选词都不会触发关闭；键盘之上、小窗之外的那块空白仍然算「窗外」，点它照样关闭小窗。

判定靠无障碍窗口列表里 `type=2`（`TYPE_INPUT_METHOD`）的窗口取边界（服务已声明 `flagRetrieveInteractiveWindows`）。键盘增减窗口会触发 `typeWindowsChanged`，遮罩随之重排。

> 遮罩重排有一拍延迟，所以点击时**还会拿落点再比一次**当前键盘区域，落在键盘里就直接忽略（日志 `OUTSIDE_TAP_IME_IGNORED`）。这层兜底是为了「键盘刚弹出、遮罩还没来得及收缩」的那一瞬间准备的。

## 第 5 步：验证「更多」应用面板

扇形里**最下面那一格**（三点省略号图标）就是「更多」——它固定占 0 号槽位，你固定的应用从它上面依次排开。这是原模块「复用原生侧边栏全部面板」的替代品——那一项需要往 `com.coloros.smartsidebar` 注入 Binder，无 root 下无解，只能自绘一个。

注意：**不固定任何应用时，扇形里只会显示「更多」**（早期版本会默认塞前 6 个应用，已去掉）。

1. 设置页里不固定任何应用，打开角落手势。
2. 斜向内上滑呼出扇形，滑到最下面那一格的「更多」。
3. 抬手 → 应弹出一块**圆角卡片式的小窗面板**：四周留白、半透明压暗下层，卡片内是 4 列网格铺满全部已安装应用，顶部依次是「全部应用」标题行、「已选」条、搜索框。
4. 点任意应用 → 该应用应同样**以小窗形态**打开（不是全屏）。

判读：

| 现象 | 含义 |
| --- | --- |
| 面板弹出、能滚动、点应用即小窗打开 | 正常 |
| 日志 `DRAWER_ADD_FAILED` | 面板窗口添加被拒（可能与其他 overlay 冲突） |
| 面板出来了但点不动 | 有全屏触摸条残留，检查日志里 `TRIGGER_RESIZE_FAILED` |
| 日志 `DRAWER_EMPTY` | 应用列表尚未加载完 |
| 点应用后出来的是**全屏** | 面板是可聚焦悬浮窗，刚持有过焦点就发起启动会被 ColorOS 判成非小窗场景；已插入 180 ms 等待（`DRAWER_LAUNCH_DELAY_MS`）。若仍全屏，把 `DRAWER_SELECTED` 之后的 `LAUNCH_ATTEMPT` 日志发出来 |

面板可按返回键、右上角「关闭」，或点卡片外的留白退出；搜索框能正常唤起输入法。

### 顶部的「已选」条（照魅族 Selected 段，可直接拖拽排序）

面板顶部第一条就是**已选**：标题 + `已选 N / 6` 计数 + 一排已固定的应用图标 + 一行用法提示。这是扇形里真实排列的镜像，**顺序就是扇形里的顺序**（左起第一项 = 扇形里紧挨着「更多」上面那一格）。

| 操作 | 结果 |
| --- | --- |
| **点**已选里的图标 | 直接以**小窗**启动它（省掉呼出扇形那一步） |
| **长按**已选里的图标 320ms | 图标被「拎起」（放大 + 阴影 + 深色底），**左右拖动即可换位**；划过相邻位置时给一次轻触感 |
| 松手 | 新顺序立刻写回配置，`PINS_REORDERED` 日志 |

判读：

| 现象 | 含义 |
| --- | --- |
| 长按后图标抬起、能横向拖 | 正常 |
| 只有 1 个固定项时长按没反应 | 设计如此：一项无从排序 |
| 拖完顺序没变 | 没拖过任何相邻图标的中线；`finishDrag` 只在顺序真变化时才回写 |
| 图标之间换位生硬 | 换位是「虚拟位次」算法，其余图标用 130ms 平移动画让位，不会重建视图 |

> 实现上刻意**不重排真实子 View**，只维护一份虚拟顺序：拖动中的那个跟随手指平移，其余按「虚拟位次 − 自然位次」平移一个槽位。这样每次换位都不需要 detach / attach，没有闪烁，也不用担心拖到一半被重建。
>
> 触摸全部由这个条自己接管（`onInterceptTouchEvent` 恒为 true）：条目上没有挂任何点击监听，单击 / 长按 / 拖拽三种意图按位移与时长在 `onTouchEvent` 里区分——否则子 View 会消费掉 DOWN，父视图再也收不到 MOVE，「长按后拖动」就实现不了。
>
> 图标尺寸是**自适应**的：条目等分整条宽度，图标按「槽位宽 − 6dp」算并收在 26~44dp 之间，所以固定 6 个也不会把窄屏撑破。

### 在面板里直接管理扇形（长按下方网格里的图标）

不必再退回设置页：**长按网格里任意图标**即弹出操作卡，一按即加入或移出扇形。

1. 呼出扇形 → 选「更多」打开面板。
2. 长按某个图标 → 弹出操作卡（应用名 + 「加入扇形」/「移出扇形」+「取消」）。
3. 点「加入扇形」→ 操作卡收起，该图标**右下角出现一个绿点**，表示已在扇形里，并立刻出现在顶部已选条里。
4. 关掉面板，再呼出扇形 → 这个应用已经排在里面了。

判读：

| 现象 | 含义 |
| --- | --- |
| 长按后弹出操作卡 | 正常 |
| 点「加入扇形」后提示「扇形最多固定 6 个…」 | 已达到上限，先在面板里移出一个 |
| 面板里绿点与扇形里的应用对不上 | 看日志 `PINS_APPLIED`，正常应是「扇形=N 固定=N」 |

已固定的应用在图标右下角带一个**带深色描边的强调色圆点**，在浅色和深色图标上都看得清。

两处入口改的是**同一份配置**（`SettingsStore.pinnedComponents`），所以在面板里改完，退回设置页的「管理扇形应用」会看到一致的状态，反之亦然。管理页里也能调顺序——已选中的行前面带**位次序号**，行尾有 `↑` `↓` 两个小按钮，和面板里的拖拽改的是同一份配置。管理页刻意用两下点而不是拖拽：那一页是长列表，拖动容易和滚动打架。

> 实现上有一点值得留意：操作卡是**画在面板自己窗口里的普通 View**（遮罩 + 卡片），不是 `AlertDialog`。面板由 Service 添加，没有 Activity 的 window token，普通对话框会直接抛 `BadTokenException`。
>
> 另外，面板内改固定项走的是 `ACTION_REFRESH_PINS`——只重算扇形，**不重新枚举已安装应用**。设置页那条路径（`AppManagementActivity`）也改成了同一个动作，避免每次点一下都跑一遍 `LauncherApps.getActivityList` 造成的卡顿。

应用管理页仍然保留：设置页点「管理扇形应用」进入。列表上百条，混在设置主页里会把后面的设置项顶得老远；页面里带搜索框，**不再有「只显示前 30 个」的限制**。它是「一次看全并批量挑」的入口，面板长按是「随手改一个」的入口，两者不冲突。

## 第 6 步：验证「角落点击透传」

角落触摸条是**独占窗口**：落在它方块内的所有触摸都被它消费（Android 没有把事件「还」给下层的 API）。这就是屏幕左右下角点不动的原因——不是没实现，是悬浮窗机制本身的副作用。

打开「角落点击透传」后，触摸条会把**非手势**的按压交给无障碍服务，按原坐标、原按住时长重新注入一次，等效于用户真的点在那里。长按也会被还原成长按。

### 为什么之前「开着却点不动」

无障碍注入的按压和真实按压一样，由 WindowManager 派发给**最顶层窗口**——也就是这条触摸条自己。所以老实现里那次注入会：

1. 被触摸条自己重新吃掉；
2. 而且它同样满足「短按、位移未超过 touchSlop」，于是**又触发一次注入**。

结果是无限递归，表现就是「透传显示生效中，但角落点击完全没反应」。

**修复**：注入前先把触摸条置为不可触摸（`FLAG_NOT_TOUCHABLE` + `updateViewLayout`），等约两帧（40ms）让窗口标志生效，注入，收到派发回调后立刻恢复。另外在 `CornerTriggerView` 上加了一道 `passthroughInFlight` 保险——万一属性变更还没生效、注入的按压又落到本视图上，直接丢弃，**绝不二次回放**。

1. 在某个应用里找一个位于屏幕左下角/右下角的按钮，或在桌面底部角落放个图标。
2. 轻点角落 → 应正常触发。
3. 长按角落 → 应触发长按行为。

判读：

| 日志 | 含义 |
| --- | --- |
| `CORNER_TAP_DETECTED` → `CORNER_TAP_THROUGH` | 正常透传 |
| `CORNER_TAP_DETECTED` → `CORNER_TAP_THROUGH_UNAVAILABLE` | 无障碍服务没连接（透传依赖它），不生效 |
| `CORNER_TAP_THROUGH_REPLAY` | 回放期间又命中了触摸条——说明让开没生效，本应是不会出现的 |
| `TRIGGER_TOUCHABLE_FAILED` | 窗口标志切换失败，触摸条会一直点不动（有 700ms 兜底恢复） |
| `CORNER_TAP_THROUGH_DISABLED` | 透传开关被关掉了 |
| 轻点没反应，且**没有** `CORNER_TAP_DETECTED` | 按压没落在触摸区内，或位移超过 touchSlop 被当成滑动 |

透传不会让被点击的坐标「按两次」——悬浮窗吃掉的那次不会传到下层，只有回放的那一次会生效。

> **无障碍服务的存活很关键**：它一旦被系统回收，窗外关闭和角落透传都会静默失效。日志里若反复出现 `A11Y_CONNECTED` / `A11Y_DISCONNECTED`，说明服务在掉线重连，应当把本应用加入系统的电池优化白名单、并锁定在最近任务里。

## 扇形的位置与间距（对照魅族官方）

**这一节的所有数字都是从魅族官方的呼出截图上一格一格量出来的**，是「像不像官方」的唯一基准，改动前请先读这一段：

| 量 | 官方实测 | 本实现 |
| --- | --- | --- |
| 图标中心到屏幕角落的距离（弧半径） | ≈ **屏幕短边的 70%** | `menuRadiusPercent` 默认 **70%** |
| 相邻图标**边缘**间距 | ≈ **1.15 倍直径** | `CHORD_PER_RADIUS` = 4.3（圆心距 4.3×半径） |
| 整条弧的张角（6 项时） | ≈ **60°~75°** | 同左 |
| 图标直径 | 46dp 量出来偏大 | `menuIconDp` 默认 **34dp**，滑块 24~52dp |
| 弧的中心方向 | ≈ 45°（对角线） | `CENTER_ANGLE_DEG` = 45° |
| 「更多」的位置 | 弧的**最低端** | 固定占 0 号槽位 |

**位置**：极坐标原点取**真实全屏边界**的角落，而不是 `resources.displayMetrics`——后者在 Service 里常常已经扣掉了导航栏高度，拿它当屏幕底边会让整条弧整体上移一截。

**半径**：由「扇形半径（占屏幕短边 %）」控制，默认 **70%**。滑块区间 25%~90%。

> 这里有过一次方向性错误：早期默认值是 19%，理由是「半径小才贴角」。实测官方是 70%——官方那种观感是**一条贴着角落的大弧**，不是「挤在角落里的小圈」。而且旧代码把半径上限硬编在 150dp，多数手机上 70% 根本调不到，这是「位置很不对」的直接成因之一。现在上限放到 460dp。

**观感**（0.1.7 起，对着官方截图重做了一轮）：

| 项 | 现状 |
| --- | --- |
| 整屏压暗 | **去掉了**。官方是原始图标直接浮在页面上；压暗会把图标一起压灰——用户说的「图标遮罩」就是它 |
| 引导弧线 | **去掉了**。官方没有那条弧 |
| 应用名 | **没有**。只画原始图标 |
| 白色圆盘 | **没有**（仅「更多」是白圆 + 深色三点，因为它没有图标本体，需要容器） |
| 选中态 | **图标放大**（`SELECTED_SCALE`=1.22），不是描边圈 |
| 图标间距 | 圆心距 = 4.3×半径，**随图标大小等比缩放**，不再写死 10dp |

> 早先固定 10dp 的间隙让图标挤成一团，是「太丑」的一半；白色圆盘 + 应用名 + 整屏压暗叠加成「一大坨」，是另一半。现在都按官方收敛了。

**图标**：由「图标大小（直径 dp）」控制，默认 **34dp**。

**项数多的时候**：不推半径，而是**缩图标**（下限 12dp）。推半径会让图标越来越远离角落。

**触感**：见 `Haptics.kt`，滑到新图标时一次 X 轴马达的清脆点击。

> **关于震动「为什么前几版都没有」**：0.1.4 用 `USAGE_TOUCH` 通道，对后台 Service 悬浮窗会被系统静默丢弃；0.1.5/0.1.6 改用 Composition 原语直调，但没先问马达支不支持——不支持的机型上 `vibrate()` 不抛异常也不震。0.1.7 起按「原语（先 `areAllPrimitivesSupported`）→ 预置 `EFFECT_CLICK`（先 `areEffectsSupported`）→ 定长 `createOneShot(12/28ms)`」三级兜底，**定长震动是任何马达都会执行的物理保证**。每次实际走哪一级都写日志 `HAPTIC_PATH`，再「没震」把这条日志发我就能定位断在哪。

相关常量都在 `RadialMenuView` 的 companion object 里：`MAX_SPAN_DEG`（张角上限 86°）、`CHORD_PER_RADIUS`（4.3）、`SELECTED_SCALE`（1.22）、`MIN_ICON_RADIUS_DP`（缩图下限 12dp）。

## 需要真机调优的参数（都已做成可调项）

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| 触发范围 | 96dp | 角落触摸方块的**边长**（宽高相同）。决定起手容错，也决定被挡住的面积 |
| 边缘让位 | 12dp | 屏幕左右边缘让给系统的宽度。**不影响触摸区大小**，上限 24dp |
| 底部让位 | 导航条高度（下限 20dp） | 避开底部手势导航带；比导航条高度本身更关键，见第 2 步 |
| 扇形半径 | 70%（占屏幕短边） | **「像不像官方」的头号参数**，对照魅族实测值，见「扇形的位置与间距」 |
| 图标大小 | 34dp | 扇形图标的直径。偏大就往下调 |
| 划过图标时震动 | 开 | 滑到新图标时一次 X 轴马达的清脆点击 |
| 关闭方式 | 点小窗底部小横条 | 四档循环，见第 4 步 |
| 落点横向位置 | 50%（占小窗宽度） | **校准核心参数之一**。50 = 水平中点 |
| 落点距小窗底边 | 8dp | **校准核心参数之一**。小横条在小窗底部；准星落在下沿之外时调成负值 |
| 显示关闭落点准星 | 关 | 在小窗上画出即将点击的准星，校准用 |
| 角落点击透传 | 开 | 见第 6 步 |

## 功能覆盖情况

已实现：角落手势唤出、扇形菜单（半径与图标大小可调 + X 轴马达触感 + 「更多」置于最下 + 只画原始图标、无遮罩无应用名）、以小窗启动、应用固定（**顶部「已选」条可拖拽排序** + 独立管理页 ↑↓ 调序 + 「更多」面板内长按增删）、**窗外点击关闭（点小窗底部小横条，落点可校准，见第 4 步）**、「更多」小窗式应用面板（自绘，见第 5 步）、**角落点击透传（见第 6 步）**。  
**未实现且无 root 下无等价方案**：上滑切换迷你窗。原生侧边栏「全部」面板无法复用，已用自绘的「更多」面板替代。  
原因见 [`no-root-feasibility.md`](no-root-feasibility.md)。
